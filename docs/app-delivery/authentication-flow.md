## 用户流程保持四步

1. 选择应用源码：创建隔离副本，保存原始源码，保留目标应用与配置。
2. 与 AI 改造应用：扫描语言、API、页面、存储和依赖；认证扫描只报告 unknown，不凭管理页面名猜 Token。AI 阅读真实登录、中间件、会话与权限代码，填写认证规则和源码行证据。生成容器适配、存储契约、业务技能与验证计划。认证信息不全返回模型修正；真正外部授权才提出有证据的一次性连接操作。
3. 核对部署内容：应用配置、资源与存储挂载保持原逻辑。展示修改差异和认证方案数量，认证方案已配置不代表已验证。预检、打包、语法校验仍执行，旧的单一 auth_profile 保持兼容。
4. 部署与使用：原有发布、构建、启动、健康、版本回执流程不变。认证探针使用与最终技能相同的调用器，支持每接口选择不同 profile、Cookie、Bearer 和固定请求头。每种受保护身份/权限范围必须有只读业务用例；通过后按既有启用机制启用技能。页面验证独立，pages_verified 不因 API 成功被设置为 true。

失败后：保存失败制品，读取真实文件，重新核对旧认证结论，保留原业务和配置，不重复索要猜测的令牌。

## 支持与限制

- auth_rules 支持 API/页面、精确路径/前缀、HTTP 方法、公开登录例外与冲突检测；证据必须指向存在的源码行，但这不等于机器能证明任意程序的认证语义。
- auth_profiles 支持多身份；凭据来源支持 username_env/password_env/token_env，原内置凭据保持兼容。此次未新增凭据保险库，也未迁移旧技能包中的明文配置；仅停止在生成的 Markdown/UI 中重复展示密码与 Token。
- 登录支持 HTTP JSON 账号密码、Cookie 与 JSON Token 路径；每次调用重新登录，不持久缓存会话。固定头和旧 Basic 兼容路径保留。登录失败返回脱敏错误，不静默冒充成功。
- 浏览器会话自动操作、任意 SSO/MFA、复杂 CSRF、专用签名协议不在现有调用器通用支持范围，需要应用专用适配。没有取消原鉴权或新增高权限账号。
- 本次没有修改 test 用户任务或线上应用，没有执行真实模型/服务器/安装版 GUI 端到端验收。
