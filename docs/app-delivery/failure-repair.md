# 部署失败修复

本次按用户明确指令不使用 SDD；修复分支为 `fix/app-delivery-failure-repair`，从远程 release 创建。未提交、推送或部署。

## 行为

失败页面的“诊断并修复失败”进入专项模式。后端保存失败 app.tar 快照与指纹、撤销旧制品确认；模型可通过 read_failed_file 分页读取脱敏文件。专项提示覆盖普通补充回答的旧方案复用规则。提交前要求读取失败制品；已知程序错误未产生文件变化时拒绝提案。基础设施故障允许不改代码。失败日志不会触发反馈正则驱动的自动数据库迁移。

完整业务源文件被替换成极短片段时拒绝修改；该启发式只覆盖明显异常，不替代业务语义审查。修复摘要保留实际诊断，不套用“确认已生效”。

预检在隔离目录应用提案并打包，对实际归档进行 Node.js 静态语法检查；正式打包及上传前再检查。只检查 .mjs/.cjs，排除 node_modules。不执行应用代码，不启动服务，不连接数据库。缺少 Node.js 或无适用文件时记录未执行，不宣称通过。解释器错误只显示文件与错误类型，不泄漏源码行。

界面展示专项状态、失败制品指纹、已有文件差异与准备检查。普通分析请求格式保持不变，正常四步向导保留。

## 验证与限制

后端定向测试覆盖原交付流程、实际归档语法失败、检查不执行代码、缺少 Node、归档链接拒绝、片段覆盖、快照保留、专项提示生效、无效修复拒绝和有效修复重新生成制品。前端组件测试覆盖专项请求及普通分析、配置和应用中心既有交互；生产构建通过。

本机用户 test 的失败归档被新检查器准确拦截：server.mjs / Illegal return statement。没有修改该用户任务、源码或线上数据。

尚未执行安装版桌面 GUI 实测、真实模型修复、服务器重新部署与业务验收。静态检查不保证目标 Node 版本兼容、业务完整性或修复正确；其他语言及 .js/TS/JSX 未新增语法检查。仍使用原服务器构建、启动、健康及业务验证链路，未增加本地自动运行应用。
